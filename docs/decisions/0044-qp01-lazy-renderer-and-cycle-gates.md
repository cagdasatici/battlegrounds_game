# 0044 QP01: lazy renderer chunk, on-demand assets, join/leave cycle gates (delegated design calls)

Owner delegated design decisions to the orchestrator (decision 0033). Budgets below are D values (local design choices), not verified facts.

1. Problem measured: the single `main` chunk was 5,475 kB raw / 1,987 kB gzip, so the interactive Welcome screen needed Three.js, Rapier, the arena and the map before it appeared. That exceeds the plan's 1 MB initial-shell trigger.
2. Split: `apps/client/src/gameRuntime.ts` re-exports everything that imports Three or Rapier (WebGLRenderer, GameScene, RapierCollide, CameraRig, presentation FX, CaptureCam, GameLoop). `main.ts` loads it with one dynamic `import()` the first time the arena is needed. `hasWebGL2` moved to `scene/webgl.ts` (re-exported from GameScene) so the capability check does not pull Three. No new `shell.ts` was created: `main.ts` already is the thin entry and the lazy boundary is the runtime module; an extra file would only add indirection.
3. Flow change (the cost of the split): `AppFlow.start()` no longer loads assets before Welcome. `ensureAssets()` runs once at the start of Play, Practice, room-list join and Host sparring; an asset failure is still `ASSET_FAILED` with Retry (Retry re-runs the journey step). Welcome was already an opaque panel, so nothing visible is removed. Play-to-first-frame now includes the runtime chunk on a cold, uncached start; the service worker installs it in the background while the person reads Welcome, and warm starts take it from the worker cache.
4. Service worker unchanged. The install precache still covers every manifest asset so offline launch and the Play path work. Deferring that art precache was not needed to meet the shell budget (the worker installs off the page's critical path), and changing it risks the update/offline contract (install.spec, update.spec pass unchanged).
5. Budgets asserted by `tests/browser/quality-load.spec.ts`: Welcome (unique same-origin responses until `[data-act=play]` is visible) at most 1,000,000 gzip bytes and no `gameRuntime` request; ten join/leave cycles after one warmup cycle, sampled at the settled Welcome point (and the settled in-match point for scene counts): event listeners, DOM nodes, open AudioContexts, geometries and active fx must not grow every cycle nor end above cycle 1; zero open AudioContexts at the end; heap growth at most 10 MB (D) after forced GC. Server-side, joins must equal leaves in the production process log.
6. Leaks: none found in the ten practice cycles (see QP01.md), so no ownership fix was made. Opening a second renderer per join is not a risk because GameScene is created once per page and disposed on pagehide.
7. Limits: Chromium on desktop SwiftShader, not an iPad; timings are desktop. Heap uses `Performance.getMetrics` JSHeapUsedSize after two forced GCs. Only practice rooms were cycled; FFA and sparring rooms share the same client path (`leaveRoom` + `matchCleanups`) but were not cycled here.
