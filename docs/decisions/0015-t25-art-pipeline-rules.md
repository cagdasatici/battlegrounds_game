# 0015 Original art pipeline rules (T25)

Date: 2026-11-01. Status: recorded while implementing T25; reversible by a later spec edit. All numbers are D (local design choices), not verified facts. No original game fact is claimed.

## Conflicts and gaps in the spec, and the rule chosen
1. **Shipped glTF versus runtime construction.** Section 23 asks for an "independently authored glTF 2.0 model with one consistent rig and named clips" per fighter, and AGENTS.md forbids a second asset path that can drift. Chosen: the fighter rig, parts and clips are authored once in code (`packages/shared/src/rig.ts`, `fighterDesign.ts`). The client builds the skinned meshes and AnimationClips from that data synchronously (no loader, no async join step, no added bundle code). `ops/scripts/build-art.ts` exports the identical data to `assets/fighters/<kit>.gltf`, and `assets:audit` regenerates each file and fails on any byte difference. The glTF files are therefore authoritative, verified artifacts, but the browser does not fetch them yet. A later task may switch the client to load them once a DCC authored replacement exists.
2. **Required animation ids for Ember Artificer.** The Ember Artificer ability definitions do not exist yet (T20 is in progress elsewhere). Required ids come from the specification names: the 14 base clips of section 23, `m1.1` to `m1.4` (the replicated move ids of the four hit M1 chain), `<kit>.b1` to `b4`, `<kit>.a1` to `a4`, `<kit>.activate` for every kit, plus `sv.x1` to `sv.x3` (the only contextual ids the spec names). Contextual ids for the other kits (T23 and later) will extend `abilityClipIds` when defined. A test proves every shipped ability definition has a clip. The visual archetype for each Artificer move is a guess from its working name and affects presentation only.
3. **Clip duration versus gameplay timing.** Authored clip lengths are arbitrary. When the replicated action has a length in ticks, the clip is time scaled (clamped 0.25x to 4x) to fit it; with no length it plays at authored speed. Clips never feed back into timing, hits or hitboxes (section 23, AGENTS.md).
4. **Cel shading and outline.** Section 23 requires three tonal bands, one directional light plus a hemisphere ambient, one shadow casting light (shadow map 1024 on medium and high, disabled on low), and no full screen post processing. Chosen: `MeshToonMaterial` with a 3x1 nearest-filtered ramp, vertex colours instead of textures, and a back-face inflated hull for outlines (a second mesh pass, not post processing). Adaptive quality changes only shadows and the render pixel ratio in this task; particle density belongs to T26 and the adaptive controller to T30.
5. **Pixel budget.** Section 24 gives low 0.75 M, medium 1.5 M, high 2.5 M rendered pixels with a 0.6 to 1.5 scale relative to CSS. Chosen: ratio = clamp(min(devicePixelRatio, sqrt(budget / cssPixels)), 0.6, 1.5). The base commit never set a pixel ratio, so iPad output was 1x (soft); this raises sharpness within budget.
6. **Hitboxes unchanged.** Fighter meshes keep the 1.8 m capsule footprint (soles at -0.9 m from the capsule centre); tests bound the mesh extents. Gameplay, server, protocol and the map collision artifact are untouched.
7. **Manifest for code built art.** The arena, sky and clouds are built at runtime from the collider list and have no file. They are tracked as a `code` manifest entry for `ArenaView.ts` with its SHA256, so any later change must be re-recorded with `pnpm assets:build` (a failing audit says so).
8. **License and author wording.** The manifest states "Project-original work; no third-party material; rights held by the project owner" and names the repository and the generator as author and source. This is a provenance statement, not legal advice; the owner may replace it with a specific licence.
9. **Production build gate.** Section 23 says empty provenance fails the production build, so `pnpm build` now runs `assets:audit` first (and `pnpm verify` includes it through build). The audit also fails on unmanifested files under `assets/`, embedded textures, fighters taller than 2.4 m, a missing required clip, and source strings naming Roblox, anime, fan wikis, asset rips or stock model sites.

10. **Visual direction (owner update).** The owner asked for a bright, stylized, blocky battlegrounds look. Chosen: chunky box-built fighters with large heads, saturated palettes, three-band toon shading, thick dark outline hulls, a cool rim fill light, bright sky, clean hemisphere ambient, soft PCF shadows, and crisp coloured terrain blocks with simple props. This imitates a general genre style only. No model, texture, animation, audio, UI art or layout from Roblox or any anime source is copied, extracted or traced; every shape is authored in code and the audit rejects such provenance strings. Style similarity is not a claim of fidelity to any reference game.

## Not decided here
`Ember Adept` in the lobby label differs from the specification name Ember Artificer; left unchanged (UI text, not art). Effects, audio and camera (T26), the physical iPad measurements and the adaptive quality controller (T30) are outside this task.

## Impact
New shared modules `rig.ts`, `fighterDesign.ts`, `art.ts`; client `ArenaView.ts`, `FighterModel.ts`, `FighterAnim.ts`; `FighterView` and `GameScene` rewritten (same public methods plus `setAction(text, moveId, phaseTicks)`, `render(dtSec)`, `setQuality`). `GameLoop` passes the move id, action length and frame time. Root scripts `assets:build` and `assets:audit` added; no dependency or lockfile change. No server, protocol, content hash or combat change.
